- **Homepage redesign — Phase 1: theme-switch jitter fix** (2026-09-25, user-reported: "on switching theme there is slightly jittery")
  - **Root cause, found by measuring, not guessing**: a global `*, ::before, ::after { transition: color/background-color/border-color/fill/stroke 200ms }` rule (plus a `button, a, input, select` duplicate) made every element animate its own color independently. A frame-by-frame poll of computed styles during a real toggle showed different elements settling 150ms to 455ms apart for a nominal "200ms" transition — e.g. the hero `<h1>` text was still visibly mid-fade when the background had already finished, which reads as jitter.
  - **Fix**: deleted both ambient rules. Theme switching is now a single whole-page crossfade via the View Transitions API (`document.startViewTransition`, wrapped around `flushSync(() => setTheme(...))` in `ThemeToggle.tsx` so the DOM mutation lands synchronously inside the callback). `index.css` now only styles `::view-transition-old(root)`/`::view-transition-new(root)` at 200ms ease-in-out (still matches the `ui-context.md` motion-table duration, updated to describe the new mechanism). Falls back to an instant swap (no fade, still no jitter) when `prefers-reduced-motion` is set or the API is unsupported. Existing per-component `transition-colors` classes (buttons/links' own 120ms hover transitions, per spec) are untouched — Tailwind's own utility classes, not the deleted ambient rule.
  - **Verified two ways**: (1) re-ran the same computed-style poll used to diagnose it — every structural element (body/navbar/h1/tool cards) now reaches its final value within one frame (~35ms), a couple of interactive elements have their own short 120-180ms hover-transition still running underneath, which finishes before the 200ms overlay is removed so it's never visibly exposed; (2) screenshots at 60ms/130ms into a real toggle show the *entire* page blended together at each instant (background, headline, hero image all at the same blend %) rather than one part switched and another still catching up — confirmed no layout shift (`PerformanceObserver` reported zero). `next build`, lint, `tsc` clean.

## Architecture Decisions

- **Unit-2 open questions closed as decisions (unit 3)**:
  - Theme default is `system` — system preference wins on first visit; the toggle persists an explicit choice.
  - Jade hex tokens that collide with shadcn variable names stay suffixed: `--accent-foreground-token`, `--ring-token`.
  - shadcn mappings stand: `--secondary`/`--muted` ← `--bg-surface`, `--accent` ← `--bg-hover`, `--destructive-foreground` flips ink like the accent; `--chart-*` removed.
  - `ShareMenu` social hover tints remain brand colors (not tokens).
- **Branding is still TBD** (Pixltly vs Snaply) but is now fully isolated to `src/lib/site.ts` — renaming the product is a one-line change.
- `ToolIcon` resolves the registry's Lucide icon-name strings through an explicit import map (keeps the bundle tree-shaken vs importing the full lucide icon set); adding a tool with a new icon means adding one import there.

- The registry stores the Lucide **icon name as a string** (per `ui-context.md`: "Each tool's registry entry carries its own Lucide icon name") rather than importing icon components, keeping the registry dependency-free for server-side consumers (sitemap, metadata).
- Unbuilt tools have **no route segments**; their existence is carried solely by `status: "soon"` in the registry, so nav surfaces can render them without dead links.
- The `/editor` redirect lives in `next.config.mjs` (`permanent: true`) rather than as a page-level `redirect()`, matching the "permanent redirect" rule in `code-standards.md`. If the app later moves to `output: "export"`, this must be revisited (config redirects don't apply to static export).
