- **Unit B — Metadata (EXIF) Viewer & Remover** (2026-09-18)
  - New tool at `/edit/metadata` (registry entry added, `category: "edit"`, `featured: true`, new icon `ScanSearch` added to `ToolIcon`'s import map). Parses JPEG (walks segments, decodes the APP1 "Exif" TIFF/IFD0 + Exif SubIFD + GPS IFD) and PNG (walks chunks: `tEXt`/`iTXt`/`tIME`/`eXIf` — the `eXIf` chunk is raw TIFF, reusing the exact same IFD parser as JPEG).   - **Follow-up fix (2026-09-18, found via real-world testing)**: the initial strip unconditionally deleted the *entire* EXIF/eXIf block, including `Orientation`. That tag isn't privacy data — it's how the viewer knows which way is "up" for photos whose sensor always captures landscape (very common on phones; a real Motorola test photo had `Orientation: Rotated 90° CW`). Deleting it would have left the "cleaned" download rendered sideways in any viewer that doesn't independently re-derive orientation. Fixed for both JPEG and PNG: `stripJpeg`/`stripPng` now peek the Orientation value before dropping the block, and if it's non-default (≠1) rebuild a minimal replacement (a single-tag TIFF IFD0 for JPEG's APP1, a real-CRC32'd `eXIf` chunk for PNG) — GPS/device/timestamps/camera-settings still fully removed either way. Verified via synthetic byte assertions (both formats, including an independent CRC32 cross-check on the rebuilt PNG chunk) and an end-to-end browser run whose *downloaded file* was independently re-parsed by both our own reader and by `file`/libmagic — both confirm GPS/Make gone, Orientation intact.
  - **Known, deliberate non-fixes** (raised during review, decisions deferred to the user): (1) the embedded ICC color profile (JPEG APP2 / PNG `iCCP`) is intentionally never stripped — it's not privacy data and removing it can shift colors in strict color-managed viewers; some phones (e.g. Motorola) stamp a `DeviceManufacturer` string into the ICC header itself, which is a much weaker residual fingerprint than full EXIF and was flagged to the user as an optional opt-in "strip color profile too" toggle, not yet built. (2) XMP-only GPS (rare) isn't parsed for display but the whole XMP APP1 segment is still fully deleted on strip, so it doesn't leak. (3) GPS altitude/heading and IPTC/Photoshop field contents aren't extracted, only flagged as "present" — same MVP-scope reasoning as XMP.

## Architecture Decisions

- **Unit-2 open questions closed as decisions (unit 3)**:
  - Theme default is `system` — system preference wins on first visit; the toggle persists an explicit choice.
  - Jade hex tokens that collide with shadcn variable names stay suffixed: `--accent-foreground-token`, `--ring-token`.
  - shadcn mappings stand: `--secondary`/`--muted` ← `--bg-surface`, `--accent` ← `--bg-hover`, `--destructive-foreground` flips ink like the accent; `--chart-*` removed.
  - `ShareMenu` social hover tints remain brand colors (not tokens).
- **Branding is still TBD** (Pixltly vs Snaply) but is now fully isolated to `src/lib/site.ts` — renaming the product is a one-line change.
- `ToolIcon` resolves the registry's Lucide icon-name strings through an explicit import map (keeps the bundle tree-shaken vs importing the full lucide icon set); adding a tool with a new icon means adding one import there.

- The registry stores the Lucide **icon name as a string** (per `ui-context.md`: "Each tool's registry entry carries its own Lucide icon name") rather than importing icon components, keeping the registry dependency-free for server-side consumers (sitemap, metadata).
- Unbuilt tools have **no route segments**; their existence is carried solely by `status: "soon"` in the registry, so nav surfaces can render them without dead links.
- The `/editor` redirect lives in `next.config.mjs` (`permanent: true`) rather than as a page-level `redirect()`, matching the "permanent redirect" rule in `code-standards.md`. If the app later moves to `output: "export"`, this must be revisited (config redirects don't apply to static export).
